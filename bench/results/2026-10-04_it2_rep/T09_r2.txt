[draft] Với ràng buộc **phải thu hồi session ngay lập tức** (immediate revocation), phương án **Sticky Sessions + Local Memory bị loại** vì: Khi chạy nhiều server instance, RAM của server A hoàn toàn cô lập với server B. ### Chọn: Database-backed Session (Mặc định an toàn nhất)

**Lý do:**
1. **Thu hồi tức thì tuyệt đối:** Khi cần logout (hoặc đổi password, ban user), bạn chỉ cần `DELETE FROM sessions WHERE token = ...` hoặc `UPDATE sessions SET is_active = false`. Request tiếp theo query vào DB là tạch ngay lập tức trên toàn bộ hệ thống. Không có độ trễ, không cần đồng bộ phức tạp.
2. **Tận dụng hạ tầng sẵn có:** Hầu như mọi web app đều có sẵn PostgreSQL, MySQL hoặc MongoDB. Bạn không cần xin phép đưa thêm công nghệ mới vào hệ thống.

**Cách giảm tải cho Database (vì sợ query nhiều):**
* Chỉ lưu các trường tối thiểu (`token`, `user_id`, `expires_at`, `data`).
* Đánh Index (`INDEX`) cho trường `token` để tốc độ truy vấn DB cực nhanh (thường chỉ vài mili-giây).
* Nếu app cực đông, có thể cấu hình **In-Memory Cache ngắn hạn (LRU Cache tại app)** với TTL siêu ngắn (ví dụ 30-60 giây) cho mỗi request đọc session, chấp nhận rủi ro chậm thu hồi tối đa 30-60 giây. Nếu cần *tuyệt đối tức thì*, bỏ qua bước cache này và query thẳng DB.

### Trường hợp ngoại lệ: Chọn Memcached (Nếu lệnh cấm chỉ đích danh Redis)
Nếu công ty chỉ cấm **Redis** nhưng **Memcached** được duyệt:
* **Tại sao hợp lý:** Memcached là Key-Value store in-memory tương tự Redis, hỗ trợ xóa key lập tức (`delete(token)`), giúp thu hồi session tức thì trên toàn bộ các server app mà không làm sập Database.
