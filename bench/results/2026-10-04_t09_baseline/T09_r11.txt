### Lý do quyết định: Khả năng thu hồi tập trung (Centralized Revocation)

Yêu cầu **thu hồi session ngay lập tức** (ví dụ: đổi mật khẩu, ép logout từ xa) đòi hỏi trạng thái session phải được quản lý ở một nơi mà **mọi server ứng dụng đều đọc được**.

* **Nếu dùng Database quan hệ:** Khi cần thu hồi, chỉ cần xóa dòng hoặc update trạng thái `revoked = true` trong bảng `sessions`. Request tiếp theo của user (dù đi vào bất kỳ server nào) query vào DB là bị chặn ngay lập tức.
* **Nếu dùng Local Memory + Sticky Session:** Dữ liệu nằm ở RAM của từng server riêng lẻ. Nếu hệ thống có nhiều server, việc đồng bộ lệnh thu hồi giữa các server là rất phức tạp (bạn sẽ phải tự viết cơ chế pub/sub hoặc gọi API nội bộ giữa các server — tức là đang tự "tái chế" lại Redis bằng code thủ công, vừa dễ lỗi vừa tốn công).

### Phân rã theo quy mô (Decision Rule):

1. **Hệ thống có nhiều server (Scale-out / Load Balancer):**
   * **Chọn:** Database quan hệ. 
   * **Đánh đổi:** Chấp nhận tốn một chút I/O database cho việc check session (có thể tối ưu bằng cách cache ngắn ở memory app trong vài giây nếu chấp nhận độ trễ cực nhỏ khi revoke).

2. **Hệ thống Monolith chạy độc lập đúng 1 instance duy nhất (Single Server):**
   * **Chọn:** Local Memory (RAM).
   * **Lý do:** Nhanh tuyệt đối, không chạm database, code cực kỳ đơn giản (`Map` hoặc `Dictionary` trong RAM) và việc revoke chỉ là xóa key khỏi RAM đó.

**Kết luận:** Trừ khi app của bạn chỉ chạy duy nhất 1 server và không có kế hoạch scale, **Database quan hệ** là lựa chọn an toàn và đúng đắn nhất để vừa đáp ứng lệnh cấm Redis, vừa đảm bảo tính năng thu hồi session tức thời trên môi trường nhiều server.
