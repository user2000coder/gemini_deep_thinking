**Lý do:**
Yêu cầu **thu hồi session ngay lập tức** kết hợp với việc **không có Redis** loại bỏ hoàn toàn phương án In-Memory nếu ứng dụng chạy từ 2 instance trở lên.

* **Tại sao In-Memory thất bại:** Khi chạy nhiều server (multi-instance), session nằm rải rác trên RAM của từng server. Khi cần thu hồi session (ví dụ: user bấm Logout hoặc bị khóa tài khoản), server A xóa session trong RAM của nó, nhưng server B vẫn còn giữ session đó trong RAM. Không có Redis (thiếu cơ chế Pub/Sub trung tâm), bạn rất khó đồng bộ việc xóa RAM giữa các server.
* **Tại sao Database thắng:** Database đóng vai trò là "Single Source of Truth". Việc thu hồi session chỉ là một câu lệnh `DELETE` hoặc cập nhật trạng thái `is_active = false` vào bảng session. Mọi instance của app đều truy vấn vào đây, nên session sẽ mất hiệu lực **ngay lập tức** trên toàn hệ thống.

**Đánh đổi & Giả định cần lưu ý:**
* **Đánh đổi:** Mỗi request (hoặc định kỳ ngắn) sẽ phải query vào DB để kiểm tra session, làm tăng I/O.
* **Giả định:** DB của bạn đủ sức chịu thêm tải đọc/ghi session. Nếu traffic lớn, cần tối ưu bằng cách kết hợp caching ngắn ở bộ nhớ ứng dụng (ví dụ: cache session ID hợp lệ trong RAM tối đa 30-60 giây) đi kèm cơ chế invalidation khi có lệnh thu hồi gấp.
