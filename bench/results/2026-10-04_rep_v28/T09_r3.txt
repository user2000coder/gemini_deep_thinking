### Lý do quyết định:

Khi đặt yêu cầu **thu hồi session ngay lập tức** cạnh ràng buộc **không dùng Redis**, **In-Memory + Sticky Sessions** sẽ phát sinh vấn đề lớn nếu ứng dụng scale lên nhiều hơn 1 server:

1. **Vấn đề thu hồi trên multi-server:** Nếu user đổi mật khẩu hoặc bịForce Logout ở Server A, nhưng request tiếp theo lại được Load Balancer điều hướng sang Server B (hoặc Sticky session bị lỗi/reset), Server B vẫn giữ session cũ trong RAM. Không có Redis làm trung gian để đồng bộ trạng thái hủy, việc thu hồi tức thì trở nên rất phức tạp (phải cài thêm cơ chế inter-server communication).
2. **Database giải quyết việc này tự nhiên:** Mọi server backend đều tra cứu một nguồn sự thật duy nhất (Single Source of Truth). Khi cần thu hồi, chỉ cần `DELETE` hoặc đổi cờ `revoked = true` ở DB. Ngay lập tức, mọi request từ mọi server check vào DB đều sẽ bị từ chối.
3. **Độ bền:** App restart hoặc deploy code mới không làm mất toàn bộ session của user (tránh việc user bị văng ra liên tục).

### Lưu ý khi dùng Database làm session store:
* **Index:** Bắt buộc phải đánh index (`B-Tree`) trên cột `session_id` hoặc `token_hash` để tốc độ tra cứu ngang ngửa RAM (thường < 5ms).
* **Cleanup:** Cần lập lịch (Cron job) xóa các session đã hết hạn để bảng không bị phình to.

* **Đúng yêu cầu thu hồi tức thời trên multi-server:** Khi ứng dụng chạy từ 2 instance trở lên (có Load Balancer), Sticky Sessions không đảm bảo sự đồng bộ trạng thái. Nếu bạn cần tính năng "Đăng xuất khỏi mọi thiết bị" hoặc admin ép khóa session, RAM của Server A không thể ra lệnh xóa session đang nằm trong RAM của Server B. Database đóng vai trò là "Single Source of Truth": mọi request từ bất kỳ server nào cũng phải tra cứu vào DB, nên việc xóa hoặc bật cờ `revoked = true` ở DB sẽ có hiệu lực **ngay lập tức** trên toàn hệ thống.
* **Độ bền dữ liệu:** App restart, deploy code mới, hoặc server bị sập không làm mất sạch session của user.

*Lưu ý khi dùng DB:* Cần đánh index (`index`) trên cột `session_id` để tốc độ truy vấn nhanh (< 5ms) và làm cơ chế dọn dẹp (cleanup job) các session cũ hết hạn.

### 2. Khi nào có thể dùng In-Memory + Sticky Sessions?
Phương án này **chỉ khả thi** nếu ứng dụng của bạn thỏa mãn điều kiện: **Chỉ chạy trên ĐÚNG 1 server duy nhất** (single instance) và không có kế hoạch scale ngang ra nhiều server trong tương lai gần. 
* Khi chỉ có 1 server, RAM cực kỳ nhanh và việc thu hồi session chỉ là xóa một biến trong bộ nhớ.
* **Ngay khi bạn scale lên 2 servers:** Sticky sessions có thể bị lệch (do load balancer đổi định tuyến, failover, hoặc user đổi mạng), dẫn đến việc session bị mất hoặc không đồng bộ trạng thái thu hồi.

**Tóm lại:** Nếu hệ thống của bạn có hoặc sẽ có nhiều hơn 1 server, hãy dùng **Database**. Nếu chỉ chạy 1 server cố định và muốn tối ưu tốc độ tuyệt đối, có thể dùng **In-Memory**.
